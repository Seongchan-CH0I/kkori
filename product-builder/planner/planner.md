# 기획 문서
상태: 검토중 / 수정일: 2026-11-08

## 1. 서비스 요약
- **이름**: 꼬리 (kkori)
- **한 줄 정의**: 매일 기술면접 질문 하나에 답하면, AI가 면접관처럼 피드백하고 꼬리질문을 던진다.
- **대상**: 신입·주니어 개발자 취준생. 처음엔 백엔드(Java/Spring, CS, DB, 네트워크)로 시작한다.
- **핵심 루프**
  ```
  아침  알림: "오늘의 질문"
  낮    답변 작성 → AI 피드백(스트리밍) → 꼬리질문
  주말  주간 약점 리포트 → 다음 주 질문 비중 조정
  ```
- **연속 기록**: 매일 답할수록 여우 마스코트 '꼬리'의 꼬리가 길어진다.

## 2. 기능 범위
| 단계 | 기능 |
|---|---|
| MVP | 오늘의 질문, 답변 피드백(스트리밍), 꼬리질문, 질문 알림, 연속 기록 |
| 2단계 | 주간 약점 리포트, 스터디 모드 |
| 3단계 | 음성 답변, 이력서 기반 질문 |

## 3. 트래픽 가정
> 부하테스트 목표 숫자. 실사용자는 대표+스터디원이지만, 모든 수치는 "MAU 100만" 가정 위에서 계산한다.
> 숫자마다 근거를 적는다. 업계 수치는 출처를 남기고, 없으면 **가정**이라고 쓴다.

### 3-1. 기본 가정
| 항목 | 값 | 근거 |
|---|---|---|
| MAU | 1,000,000 | 가정 (기존 유지) |
| DAU/MAU (스티키니스) | **20%** → DAU 200,000 | 교육 카테고리 중간값은 10~15%, 상위 분위 20~31% ([MWM DAU/MAU 자료](https://mwm.ai/glossary/dau-mau)). 습관 루프가 가장 강한 Duolingo는 FY2025 10-K에서 39.6% ([SEC 10-K](https://www.sec.gov/Archives/edgar/data/1562088/000162828026012494/duol-20251231.htm)). 꼬리는 "하루 1문제" 데일리 트리거 구조라 교육 평균보다 높고 Duolingo보다 낮게 잡아 20% |
| DAU 상한 시나리오 | 30% → DAU 300,000 | 극한 테스트용. Duolingo 수준에 근접했을 때를 가정 |
| 몰리는 시간대 | **08:00~09:00** (아침 알림 직후) | 아침 알림이 유일한 진입 트리거다. 교육 앱 푸시 옵트인율이 Android 약 94%로 전 업종 최상위권 ([Airship 2025 푸시 벤치마크](https://www.airship.com/resources/benchmark-report/mobile-app-push-notification-benchmarks-for-2025/))이라 알림→유입 전환이 트래픽 모양을 결정한다고 본다 |
| 1시간 집중률 | DAU의 **40%** = 80,000명 | 가정 (알림 트리거형 서비스는 발송 후 1시간에 일일 세션이 몰린다고 가정) |
| 피크 10분 집중률 | 1시간 유입의 50% = DAU의 **20%** = 40,000명 | 가정 (알림 직후 10분이 가장 뾰족한 구간) |

### 3-2. 사용자당 요청 수 (1일 1세션 기준, 전부 가정)
| 구분 | 요청 | 하루 횟수 | 피크 10분 내 횟수 |
|---|---|---|---|
| 읽기 | 홈(연속 기록+오늘의 질문) | 3 | 2 |
| 읽기 | 질문 상세 | 1 | 1 |
| 읽기 | 피드백 조회·재연결 | 2 | 2 |
| 읽기 | 꼬리질문 조회 | 2 | 1 |
| 읽기 | 지난 기록·답변 히스토리 | 2 | 0 |
| **읽기 합** | | **10** | **6** |
| 쓰기 | 답변 제출 | 1 | 1 |
| 쓰기 | 꼬리질문 답변 | 1.5 | 1 |
| 쓰기 | 디바이스 토큰·알림 설정 | 0.5 | 0 |
| **쓰기 합** | | **3** | **2** |

연속 기록 갱신은 답변 제출 트랜잭션 안에서 처리하므로 별도 쓰기로 세지 않는다. (대표 담당)

### 3-3. 목표 RPS
| 지표 | 계산 | 값 |
|---|---|---|
| 평균 읽기 RPS | 200,000 × 10 ÷ 86,400 | **23** |
| 평균 쓰기 RPS | 200,000 × 3 ÷ 86,400 | **7** |
| 피크 읽기 RPS | 40,000 × 6 ÷ 600초 | **400** |
| 피크 쓰기 RPS | 40,000 × 2 ÷ 600초 | **133** |
| **부하테스트 목표 (읽기)** | 피크 × 2 여유 | **800 RPS** |
| **부하테스트 목표 (쓰기)** | 피크 × 2 여유 | **270 RPS** |
| 극한 시나리오 (DAU 30%) | 위 값 × 1.5 | 읽기 1,200 / 쓰기 400 RPS |

안전 계수 2배는 가정이다. 읽기:쓰기 = 약 3:1이고 읽기 대상(오늘의 질문, 연속 기록)이 사용자 전체에 공통이라 캐시 적중률이 높을 구조다. (대표 담당: 캐시 전략)

### 3-4. 비동기·배치 목표
| 항목 | 값 | 근거 |
|---|---|---|
| 알림 발송 | 100만 건 / 1분 = **16,667 msg/s** | 가정 (기존 유지). 전원이 같은 시각 발송 대상 |
| 동시 스트리밍 | **1,500** | 피크 10분 답변 제출 40,000건 = 67건/초, 피드백 스트리밍 1건 평균 20초 지속 가정 → 67 × 20 ≈ 1,340. 여유 포함 1,500 (기존 1,000 → 상향) |
| LLM 호출 피크 | 약 **70 호출/초** | 위 계산의 답변 제출률과 동일 |
| 주간 리포트 생성 | 100만 건 (2단계 기능) | 가정 (기존 유지) |

## 4. 요구사항
> 기능마다 배경 / 사용자 스토리 / 수용 기준 / 범위 밖 / 트래픽 특성
> API·데이터는 필요한 것만 적고 **(대표 담당)** 으로 표시한다. 여기서 백엔드 구현은 하지 않는다.

### 4-1. 오늘의 질문
**배경**
신입·주니어 취준생은 "면접 준비를 해야 한다"는 건 알지만 **무엇부터 볼지 못 정해서** 시작을 미룬다. 질문 리스트 1,000개짜리 깃허브 레포를 북마크해 두고 한 번도 안 여는 상태. 선택 피로가 착수를 막는다. 꼬리는 하루에 딱 하나만 보여줘서 결정 비용을 0으로 만든다.

**사용자 스토리**
- 취준생으로서, 앱을 열면 고민 없이 오늘 풀 질문 하나만 보여서, 바로 답변을 시작하고 싶다.
- 취준생으로서, 어제 뭘 했는지 보여서, 내가 쌓고 있다는 느낌을 받고 싶다.

**수용 기준**
- Given 로그인한 사용자가 오늘 아직 질문을 받지 않았을 때, When 홈에 진입하면, Then 오늘의 질문 1개(본문, 카테고리, 난이도)와 연속 기록이 함께 보인다.
- Given 오늘의 질문을 이미 받은 사용자가, When 같은 날 다시 홈에 진입하면, Then **같은 질문**이 보인다. (하루 1질문 고정)
- Given 사용자가 이미 지난 30일 안에 받은 질문이, When 오늘의 질문으로 뽑힐 때, Then 제외하고 다른 질문을 뽑는다.
- Given 질문 은행에 뽑을 수 있는 질문이 없을 때, When 홈에 진입하면, Then "오늘은 질문이 없어요" 빈 상태 화면을 보여주고 서버 에러를 노출하지 않는다.
- Given 날짜 경계가 지났을 때, When 자정 이후 첫 진입이면, Then **KST 기준** 새 질문으로 바뀐다.
- Given 사용자가 오늘의 질문을 건너뛰고 싶을 때, When 건너뛰기를 누르면, Then 하루 1회까지 새 질문으로 교체되고 연속 기록은 끊기지 않는다.

**범위 밖 (MVP에서 안 한다)**
- 사용자별 약점 기반 개인화 추천 → 2단계(주간 약점 리포트와 묶음)
- 카테고리 직접 선택, 난이도 직접 선택
- 백엔드 외 직군(프론트, iOS, 데이터) 질문 은행
- 질문 검색, 질문 북마크
- 과거 질문 전체 목록 열람 (내가 답한 기록만 본다)
- 하루 2문제 이상, 추가 질문 결제

**트래픽 특성**
- 읽기 압도적 (읽기 6 : 쓰기 0). 세션당 가장 많이 호출되는 엔드포인트.
- 몰리는 순간: 08:00 알림 직후 10분. 피크 읽기 RPS의 절반 가까이를 이 호출이 차지한다.
- **모든 사용자가 같은 날 같은 질문 풀을 본다 → 캐시 효율이 가장 높은 지점.** 질문 본문은 변하지 않는 데이터.

**필요한 것 (대표 담당)**
- `GET /api/today` — 오늘의 질문 + 연속 기록 + 오늘 답변 여부
- `POST /api/today/skip` — 건너뛰기
- 데이터: `question`(본문, 카테고리, 난이도, 활성 여부), `daily_assignment`(사용자, 날짜, 질문, 건너뛴 횟수)

### 4-2. 답변 피드백 (스트리밍)
**배경**
혼자 면접 준비하는 사람의 가장 큰 결핍은 **"내 답이 괜찮은지 알려줄 사람이 없다"** 는 것이다. 모범답안을 읽는 건 수동적이라 기억에 안 남는다. 내가 먼저 답하고 그 답에 대한 지적을 받는 순서여야 학습이 된다. 또 LLM 응답은 수십 초가 걸리는데 빈 화면을 보여주면 사용자는 고장났다고 판단하고 이탈한다 → 스트리밍이 기능 요구사항이다.

**사용자 스토리**
- 취준생으로서, 내가 쓴 답을 면접관 눈높이로 평가받아서, 어디가 부족한지 알고 싶다.
- 취준생으로서, 피드백이 글자 단위로 바로 나오기 시작해서, 기다리는 동안 멈춘 게 아니라고 믿고 싶다.

**수용 기준**
- Given 사용자가 답변을 10자 이상 작성했을 때, When 제출하면, Then **3초 이내 첫 토큰**이 화면에 나타나고 이어서 스트리밍된다.
- Given 피드백이 스트리밍되는 중에, When 사용자가 화면을 벗어났다 돌아오면, Then 이미 생성된 부분까지 보이고 나머지가 이어진다. (진행 중 상태 복구)
- Given 스트리밍이 중간에 끊겼을 때, When 사용자가 재시도를 누르면, Then 중복 과금 없이 저장된 피드백을 그대로 보여주거나 이어받는다. (**멱등 처리 필요**)
- Given 피드백이 끝났을 때, When 화면을 보면, Then 좋은 점 / 빠진 점 / 한 줄 정리 **3블록 구조**로 정리돼 있다.
- Given 사용자가 같은 질문에 또 제출하려 할 때, When 제출하면, Then 하루 재시도 한도(2회) 안에서만 허용하고 초과 시 안내한다.
- Given 답변이 빈값·10자 미만·질문과 무관한 길이일 때, When 제출하면, Then LLM을 호출하지 않고 즉시 입력 안내를 보여준다. (**비용 방어**)
- Given LLM 제공자가 장애일 때, When 제출하면, Then "지금은 피드백을 만들 수 없어요. 답변은 저장했어요"를 보여주고 **답변과 연속 기록은 유지**된다.

**범위 밖 (MVP에서 안 한다)**
- 점수(100점 만점) 부여 → 숫자화는 사용자 반응 본 뒤 결정
- 모범 답안 제공 → 사용자가 자기 답을 먼저 믿게 하는 흐름을 깨뜨림
- 코드 작성형 답변, 코드 실행·채점
- 음성 답변 (3단계)
- 피드백 톤 선택(엄격/다정)
- 여러 LLM 비교, 피드백 공유 기능
- 답변 수정 이력 관리

**트래픽 특성**
- 쓰기 + 장시간 커넥션 유지. 요청 수는 적지만 **1건당 비용·점유 시간이 가장 큰 기능.**
- 몰리는 순간: 08:00~08:20. 피크 동시 스트리밍 1,500, LLM 호출 약 70/초.
- 커넥션이 평균 20초 열려 있어 스레드·커넥션 풀 고갈이 가장 먼저 터질 지점. 속도 제한과 대기열이 필요하다.

**필요한 것 (대표 담당)**
- `POST /api/answers` — 답변 제출 (응답: 피드백 스트림 식별자)
- `GET /api/answers/{id}/feedback/stream` — SSE 스트리밍
- `GET /api/answers/{id}/feedback` — 완성본 재조회
- 데이터: `answer`(사용자, 질문, 본문, 제출 시각), `feedback`(답변, 상태 PENDING/STREAMING/DONE/FAILED, 본문, 토큰 사용량)
- 사용자별 LLM 호출 속도 제한, 멱등키, 실패 시 재시도 정책

### 4-3. 꼬리질문
**배경**
서비스 이름이기도 한 핵심 차별점. 실제 면접에서 떨어지는 지점은 첫 질문이 아니라 **"그럼 왜 그렇죠?"** 에 답하지 못할 때다. 외운 답은 1단 깊이에서 멈춘다. 꼬리질문은 사용자가 **외운 것과 이해한 것의 경계**를 스스로 발견하게 만든다. 동시에 세션 길이를 늘리는 리텐션 장치다.

**사용자 스토리**
- 취준생으로서, 내 답변을 근거로 한 더 깊은 질문을 받아서, 실제 면접처럼 압박을 연습하고 싶다.
- 취준생으로서, 답이 막히면 거기가 내 약점이라는 걸 알아서, 무엇을 더 공부할지 정하고 싶다.

**수용 기준**
- Given 피드백이 완료됐을 때, When 사용자가 피드백을 다 읽으면, Then **내 답변 내용에 기반한** 꼬리질문 1개가 제시된다.
- Given 꼬리질문에 답했을 때, When 제출하면, Then 그 답에 대한 피드백과 다음 꼬리질문이 이어진다. (4-2와 같은 스트리밍 규칙 적용)
- Given 꼬리질문 깊이가 **3단계**에 도달했을 때, When 3번째 답변을 제출하면, Then 더 이상 꼬리질문을 만들지 않고 "여기까지 따라왔어요" 마무리를 보여준다.
- Given 사용자가 꼬리질문에 답하고 싶지 않을 때, When 그만하기를 누르면, Then 그 날 세션을 종료하고 **연속 기록은 이미 인정된 상태를 유지**한다. (첫 답변만으로 기록 인정)
- Given 사용자가 "모르겠어요"로 답했을 때, When 제출하면, Then 비난 없이 해당 개념의 핵심만 2~3줄로 알려주고 깊이를 더 내려가지 않는다.
- Given 이전 대화 맥락이 있을 때, When 꼬리질문을 생성하면, Then 원 질문 + 사용자 답변 + 직전 피드백이 맥락에 포함된다.

**범위 밖 (MVP에서 안 한다)**
- 3단계 초과 무한 깊이
- 사용자가 꼬리질문 방향을 지정하는 기능
- 멀티턴 자유 대화(챗봇화) → 하루 1루프라는 구조를 지켜야 습관이 된다
- 꼬리질문만 따로 모아보기
- 다른 사용자의 꼬리질문 대화 열람

**트래픽 특성**
- 읽기 1~2 + 쓰기 1~1.5. 대화 맥락이 쌓여 **요청마다 LLM 입력 토큰이 증가**한다.
- 몰리는 순간: 4-2보다 5~15분 뒤. 피크가 약간 뒤로 밀려 분산되는 효과가 있다.
- 깊이 3단계까지 가는 비율을 가정 40%로 두면 피크 추가 LLM 호출 약 25/초.

**필요한 것 (대표 담당)**
- `POST /api/answers/{id}/follow-ups` — 꼬리질문 답변 제출
- `GET /api/sessions/{date}` — 그 날 전체 대화(원 질문 → 꼬리 3단) 조회
- 데이터: `follow_up`(부모 답변, 깊이 1~3, 질문 본문, 사용자 답변, 피드백), 세션 단위 묶음 키

### 4-4. 질문 알림
**배경**
습관 루프의 **신호(cue)** 담당. 사용자가 앱을 기억해서 열어주길 기대하면 안 된다. 매일 같은 시각 알림이 와야 "아침에 꼬리 하나" 가 루틴이 된다. 데일리 학습 서비스에서 알림은 마케팅이 아니라 **기능의 일부**다. 다만 알림이 많아지면 즉시 차단되므로 하루 최대 2건으로 묶는다.

**사용자 스토리**
- 취준생으로서, 매일 같은 시각 오늘의 질문 알림을 받아서, 잊지 않고 하루를 시작하고 싶다.
- 취준생으로서, 내가 원하는 시각으로 알림을 바꿀 수 있어서, 내 생활 패턴에 맞추고 싶다.

**수용 기준**
- Given 알림을 허용한 사용자가, When 설정한 시각(기본 08:00 KST)이 되면, Then 질문의 **카테고리까지 포함한** 알림을 받는다. (예: "오늘의 질문: 인덱스는 왜 B-Tree를 쓰나요?")
- Given 사용자가 알림 시각을 변경했을 때, When 저장하면, Then 다음 날부터 변경된 시각에 발송된다.
- Given 사용자가 그 날 이미 답변을 완료했을 때, When 리마인드 시각(21:00)이 되면, Then **리마인드 알림을 보내지 않는다.**
- Given 사용자가 그 날 답변하지 않았을 때, When 21:00이 되면, Then "연속 기록이 끊기기 전에" 리마인드 1건을 받는다. (하루 최대 2건)
- Given 발송 중 일부 토큰이 만료됐을 때, When 발송이 실패하면, Then 해당 토큰을 비활성화하고 **전체 발송은 계속된다.**
- Given 알림을 탭했을 때, When 앱이 열리면, Then 홈이 아니라 **오늘의 질문 답변 화면으로 바로** 진입한다.
- Given 사용자가 알림을 끈 상태일 때, When 발송 대상 산출 시, Then 대상에서 제외된다.

**범위 밖 (MVP에서 안 한다)**
- 이메일·카카오톡 알림 → 푸시 1채널만
- 사용자별 최적 발송 시각 자동 추천
- 연속 기록 위험 외 다른 종류의 알림(마케팅, 신기능, 주간 리포트)
- 알림 안에서 바로 답변 입력
- 알림 A/B 문구 테스트
- 조용한 시간대(방해 금지) 세밀 설정

**트래픽 특성**
- **발송은 쓰기 폭발, 사용자 요청은 거의 없음.** 100만 건을 1분에 = 16,667 msg/s.
- 몰리는 순간: 08:00:00 정각 1분. 서비스 전체에서 가장 뾰족한 스파이크.
- 발송 직후 1~10분이 API 읽기 피크를 만든다 → **알림이 모든 트래픽의 트리거.**
- 배치·메시지 큐 설계의 핵심 대상. (대표의 Kafka / Spring Batch 모듈과 직결)

**필요한 것 (대표 담당)**
- `PUT /api/me/notification` — 알림 시각·on/off 설정
- `POST /api/me/devices` — 디바이스 토큰 등록
- 발송 배치: 시각별 대상자 조회 → 큐 적재 → 워커 발송, 실패 토큰 정리
- 데이터: `device_token`, `notification_setting`(시각, 활성), `notification_log`(멱등키로 중복 발송 방지)

### 4-5. 연속 기록
**배경**
습관 루프의 **보상(reward)** 담당. 학습 서비스의 이탈은 "효과를 못 느껴서"가 아니라 "쌓인 게 없어 보여서" 일어난다. 눈에 보이는 누적치가 있으면 "여기서 끊기면 아깝다"는 손실 회피가 작동한다. 꼬리는 숫자 대신 **여우 꼬리 길이**로 보여줘서 브랜드와 지표를 한 몸으로 만든다. D1·D7 리텐션에 직접 붙는 기능.

**사용자 스토리**
- 취준생으로서, 답할 때마다 꼬리가 길어지는 걸 봐서, 내가 쌓고 있다는 걸 느끼고 싶다.
- 취준생으로서, 하루 빠뜨렸을 때 전부 날아가지 않아서, 포기하지 않고 돌아오고 싶다.

**수용 기준**
- Given 사용자가 오늘 **첫 답변을 제출**했을 때, When 제출이 성공하면, Then 연속 기록이 +1 되고 꼬리가 한 단계 길어지는 변화가 보인다. (꼬리질문 답변은 추가로 세지 않는다)
- Given 피드백 생성이 실패했을 때, When 답변은 저장됐으면, Then **연속 기록은 인정된다.** (AI 장애로 사용자가 손해 보지 않는다)
- Given 사용자가 어제 답하고 오늘도 답했을 때, When KST 날짜가 연속이면, Then 연속 일수가 이어진다.
- Given 사용자가 하루를 빠뜨렸을 때, When 다음 날 답변하면, Then 연속 기록은 1로 초기화되지만 **누적 답변 수와 최장 기록은 보존**된다.
- Given 사용자가 연속 7일·30일에 도달했을 때, When 달성하면, Then 꼬리 모양이 눈에 띄게 달라지는 마일스톤을 보여준다.
- Given 같은 답변이 중복 제출됐을 때, When 하루에 두 번 집계되려 하면, Then 연속 기록은 **하루 1회만** 증가한다. (멱등)
- Given 사용자가 홈에 진입했을 때, When 연속 기록을 조회하면, Then 현재 연속 일수 / 최장 기록 / 누적 답변 수가 보인다.

**범위 밖 (MVP에서 안 한다)**
- 스트릭 프리즈·보상 아이템(하루 메우기)
- 랭킹, 친구 비교, 리더보드 → 첫 사용자가 10명 수준이라 비교가 오히려 역효과
- 배지·업적 시스템 전체
- SNS 공유 이미지 생성 → 그로스에서 손으로 먼저 검증
- 포인트·재화·결제
- 잔디(기여도 그래프) 형태의 연간 뷰

**트래픽 특성**
- 읽기 중심 (읽기 3 : 쓰기 0). 홈 진입마다 조회되므로 **4-1과 같은 응답에 묶어서** 호출 수를 줄인다.
- 쓰기는 답변 제출 트랜잭션에 포함 → 별도 쓰기 RPS를 만들지 않는다.
- 몰리는 순간: 08:00 알림 직후. 자정 전후 날짜 경계에서 "오늘 포함 여부" 판정이 흔들릴 위험 구간.
- 사용자별 데이터라 공용 캐시가 안 되는 읽기 → 4-1과 달리 캐시 전략이 다르다. (대표 담당)

**필요한 것 (대표 담당)**
- 연속 기록은 `GET /api/today` 응답에 포함 (별도 엔드포인트 만들지 않음)
- 데이터: `streak`(사용자, 현재 연속, 최장 연속, 마지막 인정 날짜, 누적 답변 수)
- KST 기준 날짜 처리 규칙, 하루 1회 멱등 증가

## 6. 그로스
> 첫 사용자는 대표 + 스터디원 5~10명. 획득(Acquisition)보다 **활성화(Activation)와 D7 리텐션** 하나만 본다.

### 6-1. 온보딩
목표: 가입 후 **5분 안에 첫 답변 1건 제출**. (활성화 기준)
화면 4장, 문장은 짧게. (designer에게 그대로 전달)

1. **시작**
   - "면접 준비, 뭐부터 볼지 정하다가 하루가 갑니다."
   - "꼬리는 하루에 질문 하나만 줍니다."
2. **핵심 루프**
   - "답하면 AI가 면접관처럼 피드백합니다."
   - "그리고 꼬리질문이 따라옵니다. 외운 건지 아는 건지, 거기서 갈립니다."
3. **알림 권한 요청** (권한 요청 전에 이유를 먼저 말한다)
   - "아침 8시에 질문 하나 보내드릴까요?"
   - "알림이 없으면 하루 루틴이 안 생깁니다. 시간은 나중에 바꿀 수 있어요."
   - 버튼: `8시에 받기` / `시간 고르기`
4. **첫 질문 바로**
   - "첫 질문입니다. 완벽하게 쓰지 않아도 됩니다."
   - "면접장에서 말하듯 세 문장만 써보세요."
   - 빈 화면 공포를 줄이려 입력창에 플레이스홀더: "예: 인덱스는 조회를 빠르게 하려고 쓰는데요..."

연속 기록 첫 보상 문구: "꼬리가 생겼어요. 내일 또 오면 길어집니다."

### 6-2. 초대 방식
공개 배포·마케팅은 하지 않는다. 클로즈드 10명.
1. **대표가 스터디 채널에 직접 공유** — 링크 1개 + 2문장. "내가 만든 면접 질문 앱이야. 하루 하나만 답하면 AI가 꼬리질문 던져. 2주만 써보고 욕해줘."
2. **초대 코드 없음.** 회원가입 장벽을 늘리지 않는다. 대신 접근 인원은 허용 목록으로 제한한다. (대표 담당)
3. **같이 쓰는 사람 보이기는 MVP에서 안 한다.** 10명 규모에선 비교가 압박이 된다. (4-5 범위 밖과 일치)
4. 2주 뒤 스터디원 각자 1명씩만 데려오기 → 20명. 그 이상 확장은 부하테스트 끝난 뒤에 판단.

### 6-3. 피드백 수집
| 방법 | 언제 | 무엇을 묻나 |
|---|---|---|
| 앱 안 한 줄 질문 | 3일차 답변 완료 직후 | "오늘 피드백, 면접관 같았나요?" 좋다/애매하다 2택 + 선택 입력 |
| 스터디 채널 비정기 질문 | 1주차 끝 | "어제 왜 안 열었어요?" — 이탈 이유를 직접 묻는다 (리텐션 가설 검증) |
| 대표 직접 사용 일지 | 매일 | 대표도 사용자다. 매일 쓰며 걸리는 지점을 planner.md 열린 질문에 쌓는다 |
| 지표 | 매주 | D1·D7 리텐션, 평균 꼬리질문 깊이, 첫 답변까지 걸린 시간 (대표 담당: 이벤트 로깅) |

판단 기준: **2주 뒤 D7 리텐션이 10명 중 4명 미만이면 기능을 더 넣지 말고 꼬리질문 품질을 고친다.** 습관 루프가 안 돌 때 기능 추가는 전부 낭비다.

## 7. 열린 질문
기존
- 배포 형태: 일반 웹 vs 토스 미니앱
- LLM 제공자
- 질문 은행 출처

이번에 생긴 것 (대표 결정 필요, 각 추천안 1 + 대안 1)
1. **알림 채널** — 추천: 웹 푸시 1채널. 대안: 이메일 1채널. 배포 형태가 웹이면 iOS 웹푸시 제약 때문에 "16,667 msg/s" 시나리오를 뭘로 검증할지가 바뀐다. 4-4 전체가 이 결정에 걸려 있다.

### 해설
- MVP 범위는 **습관 루프(cue-routine-reward)** 세 축에 각각 하나씩만 배치했다. 알림=cue, 질문·피드백·꼬리질문=routine, 연속 기록=reward. "범위 밖"에 점수·랭킹·모범답안을 전부 뺀 이유는 루프가 돌기 전에 보상을 늘리면 **활성화 지표가 오염되어 리텐션 원인을 못 읽기** 때문이다.
- 백로그는 RICE 대신 **MoSCoW**를 썼다. 사용자 10명 규모에선 Reach 값이 전부 같아 RICE 점수가 의미를 잃고, 대신 "없으면 출시 불가"라는 의존성 판단이 유용하다.
- 트래픽 수치는 **알림 발송 → 읽기 피크 → 스트리밍 점유**라는 단일 인과 사슬로 엮었다. 덕분에 DAU/MAU 하나만 바꿔도 모든 목표치가 같이 움직여서, 대표가 부하테스트 시나리오를 한 변수로 조절할 수 있다.
