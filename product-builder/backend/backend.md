## 0-2. 스키마 (안)

```
member
question             카테고리, 난이도, 활성
daily_assignment     member, service_date, question, skip_count   UK(member, service_date)
answer               member, service_date, depth 0~3, parent_id, body
                                                              UK(member, service_date, depth)
feedback             answer 1:1, status, 3블록, generated_offset, token_usage
streak               member, current, longest, last_counted_date, total_answers
notification_setting member, send_at, enabled
```

**`follow_up` 테이블을 만들지 않는다.** 원 질문 답변과 꼬리질문 답변은 구조가 같다. `answer`에 `depth 0~3` + `parent_id`만 두면 된다. designer가 세 화면을 하나로 합친 근거("할 행동이 같다")와 같은 이유이고, 피드백 생성 로직도 한 곳으로 모인다.

**날짜는 `service_date DATE`를 KST로 계산해 저장한다.** `created_at`에서 매번 시간대를 변환해 비교하면 인덱스를 못 타고 자정 경계 버그가 숨는다. "하루 1질문·하루 1증가"가 전부 날짜 동일성 비교라 DATE 컬럼이 맞다. DB 세션 시간대는 UTC로 고정하고(=`docker-compose.yml`), "하루"를 판정하는 책임은 애플리케이션에 둔다.

**30일 중복 제외**는 `daily_assignment`를 `(member, service_date)` 인덱스로 역순 30건 조회해 푼다. 별도 이력 테이블을 두지 않는다.

`feedback.generated_offset`은 모듈 0에서 쓰지 않지만 P1 스키마에 미리 넣는다. 모듈 5의 이어받기가 이 값으로 갈린다.

## 0-3. 설계 쟁점 3개

### ① 트랜잭션 경계 — LLM 호출을 트랜잭션 안에 두지 않는다
designer 요구("AI 실패와 무관하게 답변 저장·스트릭 선확정")와 성능이 같은 답을 가리킨다.

```
TX1 (짧게) : answer 저장 + streak 증가 → 커밋
              ↓ 여기서 사용자에게 응답
TX 밖       : 가짜 LLM 호출 (수십 초)
TX2 (짧게) : feedback 저장
```

트랜잭션을 열어둔 채 LLM을 기다리면 커넥션 하나가 수십 초 묶인다. 모듈 5에서 터질 병목을 모듈 0에서 미리 심지 않는 게 핵심이다.

### ② 스트릭 하루 1회 증가 = 조건부 UPDATE 한 방
조회 후 판단해서 쓰면 중복 제출에 경합이 생긴다.

```sql
UPDATE streak
   SET current = ..., last_counted_date = :today
 WHERE member_id = :id AND last_counted_date < :today
```

영향 행 수가 0이면 이미 오늘 집계된 것이다. 애플리케이션 락도 별도 로그 테이블도 필요 없다.

### ③ 오늘의 질문 배정은 요청 시 생성(lazy)
배치로 미리 만들면 08:00에 쓰기 스파이크가 생기고, 접속하지 않는 사용자 몫까지 만든다. 첫 홈 진입 때 만들고 `UK(member, service_date)` 충돌은 무시하면 동시 요청도 안전하다.

**검증한 것**
- `./gradlew assemble` 성공
- `./gradlew test` 성공 — 컨텍스트 로드, Hikari 커넥션, Flyway 실행 확인
- `./gradlew bootRun` 후 `/actuator/health` **200**, `db: UP` (MySQL 8.4 인식)

**의도적으로 그대로 둔 설정**
- `hikari.maximum-pool-size: 10` (기본값). 커넥션 풀 고갈은 모듈 5에서 측정할 대상이라 미리 키우면 병목이 가려진다.
- `jpa.hibernate.ddl-auto: validate`. 스키마는 Flyway만 만든다.
- `open-in-view: false`. 영속성 컨텍스트가 뷰 렌더링까지 열려 커넥션을 더 오래 잡는 걸 막는다.

**알려진 경고**
- `Flyway upgrade recommended: MySQL 8.4 is newer than this version of Flyway` — Flyway 11.7.2가 8.4를 검증하지 않았다는 뜻이고 동작은 한다. Flyway 13.x로 올리면 Boot 3.5 자동설정과 충돌 위험이 있고, MySQL 8.0은 2026-04 EOL이라 내려가지도 않는다. 유지하고, 마이그레이션이 이상하게 굴면 이 줄을 먼저 의심한다.

## 1. 예외 처리
- 비즈니스 예외(4xx) / 시스템 예외(5xx) 구분, 에러 코드 체계, 공통 응답 형식
- 외부 호출(LLM) 타임아웃, 과부하 시 429/503 + Retry-After

## 2. 로그
- 구조화 로그(JSON), 요청 추적 ID(MDC)
- 알림 한 건, 피드백 한 건을 요청부터 끝까지 추적할 수 있게
- LLM 요청·응답 로그의 민감정보와 양 관리

## 3. 배포
- Docker, GitHub Actions CI/CD, 환경 분리, 비밀값(LLM API 키) 관리
- 무중단 배포, 헬스체크, graceful shutdown (스트리밍 연결 중 배포하면?)

## 4. 모니터링
- Actuator + Micrometer → Prometheus → Grafana
- RED 지표, JVM·GC, 스레드 수, DB 커넥션 풀, Redis, Kafka 컨슈머 랙, LLM 응답 시간·실패율·토큰 사용량
- 알림 기준: "운영자가 지금 행동해야 하나"

## 5. LLM 스트리밍
- **가정**: 모듈 0 P6 베이스라인에서 역산한다. 측정 전에 목표치를 적지 않는다 (결정 #9)
- **예상 병목**: 응답 하나가 수십 초 동안 스레드를 점유 → 스레드 고갈, CPU 급증
- **다룰 기술**: SSE, 논블로킹(WebFlux) 또는 가상 스레드, 연결 수 제한, 끊김 후 이어받기
- **측정**: 동시 연결 수별 스레드 수, CPU, 첫 토큰까지 시간, 에러율

## 6. LLM 장애 대응
- **가정**: LLM API가 느려지거나, 한도 초과, 일시 장애
- **다룰 기술**: 타임아웃, 재시도(지수 백오프), 서킷 브레이커, 속도 제한(사용자별·전체), 대체 응답
- **측정**: 가짜 LLM 서버를 느리게/죽였을 때 장애와 무관한 API의 응답 시간 변화

## 7. 대량 알림
- **가정**: 전원이 같은 시각에 발송 대상이 된다. 규모는 P6 베이스라인에서 역산
- **예상 병목**: 발송 지연, 중복 발송, 유실, 발송사 속도 제한·장애
- **다룰 기술**: Kafka, 트랜잭셔널 아웃박스, 멱등 키, 재시도·DLQ, 우선순위 토픽
- **측정**: 전체 발송 완료 시간, 처리량, 중복률, 유실률

## 8. 대량 배치 (주간 리포트)
- **가정**: 주말 밤 전체 사용자 리포트 생성
- **예상 병목**: 처리 시간, LLM 비용, LLM 한도 초과
- **다룰 기술**: Spring Batch (청크, 파티셔닝, 재시작), 묶음 요청, 결과 재사용
- **측정**: 전체 처리 시간, 건당 비용, 실패 재처리

## 9. 캐싱
